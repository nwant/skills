# Information-design revision

Status: Implemented; source and behavioral checks completed. Browser-rendered layout remains unverified.

## Purpose and audience

The standard should help a technically competent reader who is unfamiliar with a system perform the intended reasoning task. Mechanisms need causal understanding; comparisons need decision support; references need accurate lookup; PRs need review. Adapt the audience when the user specifies another one.

A Visual explanation carries an essential relationship, state change, or comparison in its visuals. Each main visual should support an identifiable inference; prose supplies interpretation, evidence, and qualifications. The glossary definition lives in `CONTEXT.md`.

## Shared ownership

- `information-design/SKILL.md` owns reader tasks, teaching order, representation selection, visual construction, and evidence discipline.
- `information-design/WIDGETS.md` owns conditional guidance for inspection, stepping, and experimentation. Load it when evaluating an interaction, before deciding whether that interaction qualifies.
- Callers own workflows, deliverable formats, storage, persistence, asset reuse, and task-specific review. Caller templates and delivery contracts remain authoritative within those responsibilities.
- Dependencies use explicit skill invocation according to `.agents/invocation.md`. Supporting references remain with their owning skill; callers reach them through that skill.
- `which-skill` maps the human entry points and their relationships.

Keep the current two-file instruction structure. Add detail only where it changes a design decision; consolidate repeated examples and rules instead of accumulating parallel standards.

## Explanation design

- Identify the reader's question and the relationship they need to see: sequence, accumulation, ownership, dependency, comparison, or state change.
- Choose the smallest representation that exposes that relationship. Code, trees, pseudocode, diffs, and tables remain useful when implementation or exact lookup is the reader's task.
- Establish the thesis and overview early. Teach mechanisms through concrete examples, comparisons through decision criteria, and performance investigations through measured constraints. Replace mandatory bottleneck-first ordering with this task-dependent choice.
- Expand the representation catalog to include timelines, swimlanes, storyboards, execution steppers, aligned message stacks, range diagrams, coverage matrices, and quantitative plots.
- Preserve identity across views through consistent names, shapes, positions, and meaningful color. Distinguish added, removed, retained, and transferred state.
- Label connections with the action or payload they represent. Place explanatory labels beside the relevant visual elements.
- Align comparable states and use consistent scales for comparable quantities. Connect overview and detail views when their correspondence would otherwise be difficult to follow.
- Replace fixed node and control counts with readability and task-coherence criteria. Short prose is allowed in table cells when it supports comparison.
- Use neutral structure and a small semantic palette. Pair color with labels or shapes, and distinguish entity identity from emphasis on the current change. Remove the fixed teal/amber-only restriction.

## Interaction

Static views are the default when they expose the relationship clearly. Add interaction for a specific investigative benefit, and make the initial view useful before input.

- **Inspect:** select a recorded item and reveal its supporting detail; maintain a traceable connection to the evidence.
- **Step:** move through recorded states or states generated by explicit executable rules; label schematic examples.
- **Experiment:** change inputs through a disclosed model with defensible assumptions, parameters, and limits.

Remove the continuous-variable gate. Formulas and live numerical recomputation apply where the model calls for them, not to every interaction. Motion should explain a meaningful transition; support inspection through stepping, pausing, or static comparison where appropriate.

Standalone artifacts may default to one offline HTML file. Other callers can retain their own packaging: shared local assets for teaching, Markdown for PRs, and the output contracts of the active rendering environment.

## Evidence and verification

Distinguish recorded observations, implementation facts, interpretations, and illustrative examples. Preserve measurement meaning from the source through the headline, labels, and conclusions. Quote matching, semantic support, and execution success are different outcomes. Identify estimated or illustrative quantities and disclose assumptions where they affect interpretation.

For rendered explanations, inspect an intended desktop width and a narrow width, and exercise representative interaction states. When rendering tools are unavailable, perform the available source checks and report what remains unverified; delivery can proceed. Assess whether the visual supports the intended inference, and claim reader comprehension only when it has actually been tested.

Evaluate the revision against four representative cases:

1. The run explanation: readers can trace context growth and reset, recovery from a malformed reply, and the distinction between execution status and quote validation.
2. A compact PR summary: the standard respects the caller's template and produces an appropriately brief account of the change.
3. A source-based Synthesis: the standard preserves source boundaries and evidence fidelity while choosing a useful teaching order and representations.
4. A visual teaching lesson: the standard supports the explanation while preserving lesson progression, exercises, and reusable local assets.

These are behavioral evaluations alongside reference and instruction checks. They do not establish measured learning outcomes without reader testing.

## Validation results

Four fresh-context skill exercises produced artifacts in a scratch directory outside the repo:

- **Run:** a standalone explanation with a phase strip, message-stack comparison, prompt bars, failure storyboard, and separate execution and quote-validation outcomes. All 13 prompt values and their proportional widths were checked against the report; the source copy matches the original.
- **PR:** a compact Summary, Evidence, and Merge Danger body using a literal diff. A fresh reproduction showed the stale value before the change and the updated value after it; the body accurately identified that the reproduction prints results without assertions.
- **Synthesis:** a static, source-bounded comparison selecting the fixture service that meets the stated requirements. Independent citation review found no unsupported or uncited claims. Source inspection confirmed the recommendation and explicit evidence gaps.
- **Teaching:** a queue storyboard, one practice task, and a reference card using the existing course stylesheet and extracted reusable assets. Local links, JavaScript syntax, eight answer paths, and input reset were checked. No learning record claimed unobserved learner performance.

These exercises check particular outputs, not measured comprehension or an improvement over a controlled baseline. Browser access was unavailable, and native Chrome inspection timed out; desktop and narrow layout remain unverified. Teaching feedback was exercised in a DOM stub, not a browser.

The six changed skills passed standard frontmatter and body validation after accounting for the repo's unchanged `disable-model-invocation` and `argument-hint` extensions, which the bundled validator does not recognize. Invocation pairs, explicit dependency reachability, local links, and prose punctuation were checked separately. The docs question hunt used this interview and the local changelog; GitHub issue lookup was unavailable because the CLI could not connect.
